## Context

当前 `app.js` 是一个约 1370 行的单文件，包含以下主要职责：
- 应用初始化和配置
- 视图切换和渲染
- 事件绑定和键盘快捷键
- 主题管理
- 模态框管理
- 导出导入功能
- Toast 通知

这种"上帝类"架构导致：
- 代码难以理解和维护
- 单元测试困难
- 添加新功能需要修改现有代码
- 违反 SOLID 原则

项目是一个纯前端应用，使用原生 JavaScript，无框架依赖。

## Goals / Non-Goals

**Goals:**
- 将 `App` 类重构为多个独立的、职责单一的管理器类
- 遵循开闭原则，通过扩展而非修改来增强功能
- 保持向后兼容，不改变现有功能行为
- 提高代码可测试性和可维护性

**Non-Goals:**
- 不改变业务逻辑和行为
- 不引入外部依赖或框架
- 不改变数据模型或 API
- 不改变现有的状态管理机制

## Decisions

### D1: 管理器架构模式
**决策**: 使用管理器模式，将 `App` 类拆分为多个独立的管理器类。

**理由**:
- 管理器模式适合将相关功能分组，提高代码组织性
- 每个管理器职责单一，易于理解和维护
- 管理器之间通过 App 类协调，保持低耦合

**替代方案**:
- 模块化导出：将功能拆分为独立模块，通过导入使用
  - 缺点：难以共享状态和上下文
- 观察者模式：使用事件发布/订阅机制
  - 缺点：增加复杂度，对于当前项目规模过度设计

### D2: 管理器依赖注入
**决策**: 每个 Manager 接收必要的依赖（app、state、i18n 等）作为构造函数参数。

**理由**:
- 显式依赖，便于测试和替换
- 避免全局状态污染
- 保持 Manager 之间的独立性

### D3: App 类职责转变
**决策**: App 类从"上帝类"转变为"协调器"，主要职责是初始化和管理其他管理器。

**理由**:
- 保持向后兼容，App 类仍然是应用入口
- 集中管理生命周期和协调逻辑
- 提供统一的配置和初始化入口

### D4: 文件组织结构
**决策**: 创建 `js/managers/` 目录，每个管理器独立文件。

```
js/
├── app.js (重构后，主要负责协调)
├── managers/
│   ├── ViewManager.js
│   ├── EventManager.js
│   ├── UIRenderer.js
│   ├── ThemeManager.js
│   ├── ExportImportManager.js
│   ├── ModalManager.js
│   └── NotificationManager.js
└── ...
```

**理由**:
- 清晰的目录结构，易于导航
- 每个文件职责单一
- 符合前端项目的常见组织方式

### D5: 向后兼容策略
**决策**: 保持 `App` 类的公共 API 不变，内部实现逐步迁移到管理器。

**理由**:
- 降低重构风险，可以逐步迁移
- 不影响现有功能
- 便于测试和验证

### D6: 事件处理委托
**决策**: EventManager 负责事件绑定，但事件处理函数仍保留在 App 类或专门的 Handler 中。

**理由**:
- EventManager 专注于事件绑定逻辑
- 业务逻辑保持可访问性
- 避免过度抽象

## Risks / Trade-offs

### Risk 1: 重构过程中引入 Bug
**风险**: 在迁移代码过程中可能引入功能回归

**缓解措施**:
- 保持向后兼容，逐步迁移
- 每个管理器迁移后进行充分测试
- 使用 Git 分支管理，便于回滚

### Risk 2: 性能开销
**风险**: 多个管理器实例可能带来轻微的性能开销

**缓解措施**:
- 管理器单例模式，避免重复创建
- 优化事件委托，减少监听器数量

### Trade-off 1: 灵活性 vs 简洁性
**权衡**: 增加了文件数量和代码行数，但提高了可维护性

**决策**: 选择可维护性，因为代码质量比代码行数更重要

### Trade-off 2: 学习曲线
**权衡**: 新架构需要团队成员理解新的管理模式

**缓解措施**:
- 提供清晰的文档和注释
- 遵循常见的设计模式

## Migration Plan

### 阶段 1: 创建管理器基类和接口
1. 创建 `js/managers/` 目录
2. 创建基础管理器类
3. 定义管理器接口和依赖关系

### 阶段 2: 逐个迁移管理器
1. 按以下顺序迁移管理器：
   - NotificationManager (最简单，无依赖)
   - ThemeManager (简单，独立)
   - ModalManager (中等，依赖 app 和 state)
   - ViewManager (中等，依赖 state)
   - EventManager (复杂，需要注册所有事件)
   - ExportImportManager (中等，依赖 app 和 state)
   - UIRenderer (最复杂，依赖所有其他管理器)

2. 每次迁移后：
   - 运行应用验证功能
   - 检查控制台错误
   - 手动测试相关功能

### 阶段 3: 重构 App 类
1. 将 App 类中的方法委托给相应的管理器
2. 保留 App 类作为协调器
3. 清理冗余代码

### 阶段 4: 测试和优化
1. 端到端测试所有功能
2. 性能测试
3. 代码审查
4. 文档更新

### 回滚策略
- 使用 Git 分支管理，主分支保持稳定
- 每个阶段完成后创建提交点
- 如遇问题，可回滚到最近的稳定提交

## Open Questions

1. **是否需要创建基础管理器类？**
   - 当前倾向于不创建基类，保持简单

2. **UIRenderer 是否需要进一步拆分？**
   - 当前 UIRenderer 包含多个视图的渲染逻辑
   - 可能需要进一步拆分为独立的 Renderer（如 StoryRenderer, CharacterRenderer 等）
   - 建议在实现时评估

3. **EventManager 是否需要支持事件总线？**
   - 当前倾向于不实现完整的事件总线
   - 保持简单，专注于 DOM 事件绑定

4. **管理器之间的通信方式？**
   - 当前倾向于通过 App 类协调
   - 避免管理器之间的直接依赖
