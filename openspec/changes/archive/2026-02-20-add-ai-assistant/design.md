## Context

### 当前状态

BailuStory是一个基于浏览器的小说编写工具，采用管理器模式架构，包含以下管理器：
- ViewManager（视图管理）
- ThemeManager（主题管理）
- NotificationManager（通知管理）
- ModalManager（模态框管理）
- ExportImportManager（导入导出）
- EventManager（事件管理）
- UIRenderer（UI渲染）

当前章节编辑界面采用三栏布局：
- 左侧：章节列表
- 中间：章节编辑器
- 右侧：修改追踪器

### 约束条件

1. **纯前端应用**：无后端服务，所有AI调用在浏览器端完成
2. **存储限制**：配置和历史数据存储在localStorage，容量约5MB
3. **API密钥安全**：API Key需加密存储，不可明文保存在代码中
4. **响应式要求**：需适配不同屏幕尺寸，小屏幕下支持底部面板模式
5. **无外部依赖**：使用浏览器原生fetch API，避免引入额外依赖库
6. **测试要求**：根据项目规范，新代码需编写单元测试，覆盖率≥80%

### 利益相关者

- **最终用户**：小说创作者，需要简洁易用的AI辅助功能
- **开发者**：维护代码，需要清晰的架构和可测试性
- **项目规范**：遵循现有架构模式和测试规范

## Goals / Non-Goals

**Goals:**
1. 在章节编辑界面右侧添加可调整宽度、可折叠的AI助手面板
2. 支持多AI提供商（OpenAI、Anthropic、本地LLM等）的API集成
3. 提供友好的首次配置引导，通过设置按钮上的提醒图标提示用户
4. 实现对话历史记录和会话管理
5. 支持AI生成内容插入到编辑器
6. 遵循现有管理器模式架构，保持代码一致性
7. 确保所有新代码有完整的单元测试覆盖

**Non-Goals:**
1. 预设快捷操作按钮（暂不实现，留待后续扩展）
2. 流式响应输出（初期采用一次性响应，后续可扩展）
3. AI配置的导入/导出功能
4. 多配置文件管理（仅支持单一活跃配置）
5. AI内容自动保存到故事（需用户手动插入）
6. 复杂的上下文管理（初期仅提供基础上下文）

## Decisions

### 1. 架构设计：三独立管理器模式

**决策**：采用三个独立的管理器类和服务类

**实现**：
- `AIConfigManager` - 配置管理（API Key、端点、模型、参数等）
- `AIService` - 纯服务类，负责HTTP通信、请求构建、响应处理
- `AIManager` - 主管理器，协调UI交互、业务逻辑、状态管理

**理由**：
1. **职责分离**：配置、API调用、UI交互各司其职，符合单一职责原则
2. **可测试性**：AIService可独立测试，Mock更容易
3. **可扩展性**：添加新AI提供商时，只需扩展AIService
4. **符合现有架构**：与其他Manager类保持一致的开发模式
5. **依赖管理**：AIManager依赖AIConfigManager和AIService，层次清晰

**替代方案考虑**：
- **单一管理器**：所有功能合并在AIManager中
  - 优点：文件少，调用简单
  - 缺点：职责不清晰，测试困难，违反现有架构模式
  - 结论：不采用

**代码结构**：
```
js/
├── managers/
│   ├── AIConfigManager.js  # 配置管理器
│   └── AIManager.js        # AI主管理器
└── services/
    └── AIService.js        # AI服务类
```

### 2. UI布局：可调整宽度 + 可折叠面板

**决策**：
- 默认宽度：300px，支持拖拽调整（范围：200px-600px）
- 支持折叠/展开（右上角折叠按钮）
- 小屏幕（<768px）下：底部按钮 + 抽屉式面板
- 面板位置：章节编辑器右侧，替换现有修改追踪器位置

**理由**：
1. **用户习惯**：类似VS Code、Cursor等AI IDE的布局，用户熟悉
2. **空间利用**：可调整宽度适应不同内容长度
3. **响应式友好**：小屏幕下不占用宝贵垂直空间
4. **渐进增强**：折叠功能在不需要AI时释放屏幕空间

**布局示意**：

### 3. 多AI提供商支持：统一接口 + 提供商适配器

**决策**：
- 定义统一的AI服务接口
- 每个提供商实现适配器（Adapter Pattern）
- 支持的提供商：OpenAI、Anthropic、自定义端点（兼容OpenAI格式）

**理由**：
1. **可扩展性**：新增提供商只需实现适配器，不影响核心逻辑
2. **统一调用**：上层代码无需关心具体提供商
3. **灵活性**：用户可自定义端点（如本地LLM）

**接口设计**：

```javascript
// AIService 统一接口
class AIService {
    async chat(config, messages)  // 发送聊天请求
    async validateConfig(config)  // 验证配置
    getProviderInfo(config)       // 获取提供商信息
}

// 提供商适配器
class OpenAIAdapter {
    buildRequest(config, messages)  // 构建OpenAI请求
    parseResponse(response)         // 解析OpenAI响应
}

class AnthropicAdapter {
    buildRequest(config, messages)
    parseResponse(response)
}

class CustomAdapter {
    buildRequest(config, messages)
    parseResponse(response)
}
```

**配置结构**：
```javascript
{
  "provider": "openai",  // openai | anthropic | custom
  "apiKey": "sk-xxx",
  "endpoint": "https://api.openai.com/v1/chat/completions",  // custom时使用
  "model": "gpt-3.5-turbo",
  "temperature": 0.7,
  "maxTokens": 2000
}
```

**替代方案考虑**：
- **仅支持OpenAI**：简单但限制了用户选择
  - 结论：不采用，用户可能有不同需求
- **完全独立实现**：每个提供商独立类，无统一接口
  - 缺点：代码重复，难以维护
  - 结论：不采用

### 4. 首次配置引导：设置按钮提醒图标

**决策**：
- AI面板顶部设置按钮（⚙️）
- 未配置时：设置按钮显示红色徽章（⚠️或红点）
- 点击设置按钮：打开配置模态框
- 配置验证：保存时验证API Key有效性（发送测试请求）

**理由**：
1. **非侵入性**：不立即弹出模态框干扰用户
2. **持续提示**：徽章持续存在，提醒用户配置
3. **即时验证**：配置时验证API Key，避免使用时才发现错误
4. **符合用户习惯**：类似IDE设置按钮的设计

**UI流程**：
```
[首次打开AI面板]
↓
设置按钮显示红色徽章 ⚙️🔴
↓
用户点击设置按钮
↓
打开配置模态框
↓
用户填写API Key、选择提供商、模型
↓
点击"测试连接"
↓
发送测试请求
    ├─ 成功 → 保存配置 → 徽章消失
    └─ 失败 → 显示错误信息
```

**配置模态框字段**：
- 提供商选择（下拉框）：OpenAI / Anthropic / 自定义
- API Key（密码输入框）
- 端点URL（自定义提供商时显示）
- 模型选择（文本输入框，带默认值）
- Temperature（滑块：0-2，默认0.7）
- Max Tokens（数字输入框，默认2000）
- 测试连接按钮
- 保存/取消按钮

### 5. 对话历史管理：按章节存储

**决策**：
- 按章节ID存储对话历史
- 每个会话最多保存20条消息（可配置）
- 支持清空当前会话历史
- 历史数据存储在localStorage

**理由**：
1. **上下文关联**：同一章节的对话相关联
2. **存储效率**：限制消息数量避免localStorage溢出
3. **隐私安全**：数据存储在本地，不上传服务器
4. **用户体验**：切换章节自动加载对应历史

**存储结构**：
```javascript
{
  "ai": {
    "history": {
      "chapter-1": [
        { role: "user", content: "帮我续写这一段", timestamp: 1234567890 },
        { role: "assistant", content: "好的，这是续写内容...", timestamp: 1234567891 }
      ],
      "chapter-2": [...]
    },
    "historyLimit": 20
  }
}
```

**生命周期**：
- 用户发送消息 → 添加到当前章节历史
- 切换章节 → 保存当前历史，加载新章节历史
- 清空历史 → 删除当前章节历史
- 删除章节 → 删除对应历史（可选）

### 6. 内容插入：选中优先 + 光标位置

**决策**：
- AI响应显示在聊天区域
- 每条AI响应下方有"插入到编辑器"按钮
- 插入逻辑：
  1. 如果有选中文本：替换选中文本
  2. 如果有光标位置：插入到光标处
  3. 否则：追加到段落末尾

**理由**：
1. **灵活性**：用户可自由选择插入位置
2. **直观性**：按钮直接显示在AI响应下方
3. **容错性**：无选中/光标时也能插入

**实现**：
```javascript
// 插入逻辑
insertToEditor(content) {
    const selection = window.getSelection();
    
    if (selection.toString()) {
        // 替换选中文本
        const range = selection.getRangeAt(0);
        range.deleteContents();
        range.insertNode(document.createTextNode(content));
    } else {
        // 插入到当前活动输入框
        const activeTextarea = document.activeElement;
        const cursorPos = activeTextarea.selectionStart;
        const text = activeTextarea.value;
        activeTextarea.value = text.slice(0, cursorPos) + content + text.slice(cursorPos);
    }
}
```

### 7. 错误处理：分级提示 + 重试机制

**决策**：
- 网络错误：提示用户检查网络连接
- API错误（4xx）：根据状态码显示具体错误信息
- 超时错误：30秒超时，提示用户重试
- 提供重试按钮（仅对可重试错误）

**理由**：
1. **用户体验**：明确的错误提示帮助用户快速定位问题
2. **容错性**：临时网络问题可通过重试解决
3. **安全性**：不暴露敏感信息（如完整API Key）

**错误类型映射**：
```
401 Unauthorized → "API Key无效，请检查配置"
403 Forbidden → "无访问权限，请检查API Key权限"
429 Too Many Requests → "请求过于频繁，请稍后再试"
500+ Server Error → "AI服务暂时不可用，请稍后再试"
Network Error → "网络连接失败，请检查网络"
Timeout → "请求超时，请重试"
```

**重试逻辑**：
- 仅对网络错误、超时错误、5xx错误提供重试按钮
- 4xx错误不提供重试（需用户修正配置）

## Risks / Trade-offs

### 风险1：localStorage容量限制导致历史数据丢失

**风险**：localStorage限制约5MB，对话历史可能超过限制

**缓解措施**：
1. 设置合理的历史限制（默认20条消息）
2. 实现LRU（最近最少使用）策略清理旧历史
3. 存储失败时提示用户并停止保存新历史
4. 在配置中提供"清除所有历史"按钮

**监控指标**：
- 每次保存前检查localStorage剩余容量
- 警告阈值：剩余容量<1MB时提示用户

---

### 风险2：API Key泄露

**风险**：localStorage存储的API Key可能被恶意脚本读取

**缓解措施**：
1. API Key使用Base64编码（简单混淆，非加密）
2. 在控制台警告用户不要在公共电脑使用
3. 提供配置导出功能时，默认不包含API Key
4. 未来可考虑使用Web Crypto API加密（需权衡复杂度）

**注意**：
- 纯前端应用无法完全避免此风险
- 用户需自行保管API Key安全

---

### 风险3：多提供商API差异导致兼容性问题

**风险**：不同AI提供商的API格式差异可能影响功能

**缓解措施**：
1. 定义清晰的接口契约
2. 为每个提供商编写单元测试
3. 使用适配器模式隔离差异
4. 文档化支持的提供商和版本

**测试策略**：
- 测试用例覆盖所有支持的提供商
- 使用Mock服务模拟API响应

---

### 风险4：小屏幕下用户体验下降

**风险**：移动端面板可能占用大量屏幕空间

**缓解措施**：
1. 采用抽屉式设计，默认隐藏
2. 优化面板高度，使用固定高度+滚动
3. 输入区域使用紧凑设计
4. 提供快速收起按钮

**响应式断点**：
- `<768px`：底部抽屉模式
- `768px-1024px`：面板宽度缩减至250px
- `>1024px`：默认300px宽度

---

### 权衡1：简化配置 vs 功能完整性

**权衡**：初期不预设快捷操作，减少复杂度，但用户需要手动输入提示词

**理由**：
1. 快捷操作需要大量提示词工程和调优
2. 不同用户需求差异大，难以预设通用模板
3. 用户自由度更高，避免功能臃肿

**未来扩展**：
- 收集用户反馈后，可添加常用快捷操作
- 支持用户自定义快捷操作模板

---

### 权衡2：非流式响应 vs 实时体验

**权衡**：初期采用一次性响应，简单但体验不如流式输出

**理由**：
1. 实现复杂度低，快速上线
2. 避免处理流式数据的复杂性（如断开、重连）
3. 对于短文本（如小说段落），一次性响应可接受

**未来扩展**：
- 用户反馈需求强烈后，可添加流式响应支持
- 使用Server-Sent Events或WebSocket

## Open Questions

1. **API Key加密强度**：当前使用Base64简单混淆，是否需要使用Web Crypto API加密？
   - 优点：更安全
   - 缺点：增加复杂度，需要存储密钥管理逻辑

2. **历史数据导出**：是否需要支持导出对话历史（如导出为文本文件）？
   - 场景：用户可能需要备份或分享对话内容

3. **批量操作**：是否需要支持批量请求（如一次性续写多个章节）？
   - 场景：用户可能需要快速生成大量内容

4. **上下文管理**：是否需要自动管理上下文窗口（如当上下文超限时自动截断）？
   - 当前方案：简单限制历史消息数量
   - 高级方案：智能摘要旧消息，保留关键信息

5. **多语言支持**：AI面板的提示词、错误信息是否需要国际化？
   - 当前项目支持中英文切换
   - AI面板需要与项目i18n系统集成

6. **性能优化**：是否需要实现请求节流/防抖，避免用户快速连续发送请求？
   - 场景：用户可能快速点击"发送"按钮

**待决策事项**：
- Q1：API Key加密方案（优先级：中）
- Q5：多语言支持（优先级：高，与项目一致）
- Q6：请求节流（优先级：中）

其他问题可在后续迭代中根据用户反馈决定。
