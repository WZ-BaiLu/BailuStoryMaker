## Context

当前 BailuStory 应用使用 Manager 模式管理各功能模块，已存在 UIRenderer、ViewManager、AIManager 等管理器。段落编辑界面目前仅支持基础的段落添加和编辑功能，缺少可视化的时间线追踪能力。

系统现状：
- 段落编辑器位于左侧，右侧为 AI 面板
- 角色、道具、场景（setting）作为独立模块管理
- **段落数据结构已包含 `changes` 字段**，记录角色和道具状态变化：
  ```javascript
  {
    id: 'paragraph-1',
    content: '...',
    changes: {
      characters: [],
      items: []
    }
  }
  ```
- AIManager 已集成基础 AI 对话和工具调用能力
- UIRenderer 负责所有 UI 渲染逻辑

约束条件：
- 需保持与现有 UI 风格和交互模式一致
- 不能破坏现有数据模型向后兼容性（changes 字段已存在）
- 必须支持现有键盘快捷键和事件系统
- 时间线面板需适配深色/浅色主题

## Goals / Non-Goals

**Goals:**
1. 创建时间线管理器（TimelineManager）独立管理时间线面板逻辑
2. 在段落编辑器右侧添加可展开/折叠的时间线分页面板
3. 实现段落与时间线节点的双向同步（段落变化自动更新时间线，点击节点跳转段落）
4. 追踪并显示每个段落对角色状态和道具分配的影响
5. 为 AI 添加工具，支持根据剧情内容自动修改角色/道具状态
6. 提供时间线状态筛选（角色/道具/全部）和持久化

**Non-Goals:**
1. 不在此改动中实现角色/道具状态的图形化编辑器
2. 不涉及时间线的动画效果和过渡（仅基本展开/折叠）
3. 不实现多级时间线（仅段落级别）
4. 不涉及段落间的依赖关系或因果关系分析

## Decisions

### 1. 时间线管理器架构

**决策：** 不创建独立的 TimelineManager，时间线逻辑直接在 UIRenderer 中实现，读取段落已有的 `changes` 数据

**理由：**
- `changes` 字段已存在于段落数据结构，无需额外管理
- 时间线是纯 UI 展示功能，不涉及复杂业务逻辑
- 避免管理器类过多，简化架构
- 时间线状态（展开/折叠、筛选选项）使用 localStorage 持久化即可

**替代方案考虑：**
- 创建独立 TimelineManager：增加复杂度，职责过于单一
- 扩展现有 ViewManager：ViewManager 职责是视图切换，不适合承担渲染细节

### 2. 数据模型使用

**决策：** 使用段落现有的 `changes` 字段，不做额外修改

**现有数据结构：**
```javascript
{
  id: 'paragraph-1',
  content: '...',
  changes: {
    characters: [],    // 角色变化数组
    items: []         // 道具变化数组
  }
}
```

**理由：**
- 数据结构已存在且完整，无需扩展
- 向后兼容性天然保证
- 避免数据冗余和维护成本

**替代方案考虑：**
- 扩展 changes 字段结构：已满足需求，无需修改

### 2. 时间线面板布局

**决策：** 在段落编辑器容器右侧使用 Flexbox 布局，时间线面板初始宽度 300px，支持折叠

**理由：**
- Flexbox 响应式布局适配不同屏幕尺寸
- 固定初始宽度确保视觉一致性
- 折叠功能提供更大的编辑空间

**替代方案考虑：**
- 使用绝对定位：可能与现有布局冲突
- 可拖拽调整宽度：增加实现复杂度，后续可迭代

### 4. AI 工具设计

**决策：** 在 AIManager 中新增两个工具方法：`updateCharacterState` 和 `updateItemState`

**工具接口设计：**
```javascript
{
  name: 'updateCharacterState',
  parameters: {
    characterId: 'string',
    changes: {
      attributes: 'object',
      emotionalState: 'string'
    },
    paragraphId: 'string'
  }
}
```

**理由：**
- 工具化设计便于 AI 理解和调用
- 与段落关联确保状态变化可追溯
- 复用现有 AIManager 工具注册机制

**替代方案考虑：**
- 直接修改角色对象：AI 调用不清晰，难以追踪
- 使用 JSON-RPC 接口：过度设计，增加复杂度

### 3. 状态持久化策略

**决策：** 时间线面板状态（展开/折叠、筛选选项）使用 localStorage 持久化，状态变化数据使用段落已有的 `changes` 字段

**理由：**
- 面板状态是用户偏好，独立存储符合使用场景
- 状态变化数据已在段落的 `changes` 字段中，随段落保存
- 复用现有 localStorage 机制（ViewManager 已使用）

**替代方案考虑：**
- 全部存储在 story 对象：增加故事文件体积，混合了用户偏好和内容数据
- 使用 IndexedDB：对于少量数据存储过度设计

### 5. 状态变化可视化

**决策：** 使用图标 + 颜色区分变化类型（角色变化用蓝色图标，道具变化用绿色图标，新增用 '+'，修改用 '~'，删除用 '-'）

**理由：**
- 视觉符号直观易懂
- 颜色区分增强可读性
- 符合现代 UI 设计习惯

**替代方案考虑：**
- 仅使用文本标签：占用空间大，可读性差
- 使用复杂图表：开发成本高，可能影响性能

## Risks / Trade-offs

### Risk 1: 时间线节点数量过多影响性能

**描述：** 长章节可能有上百个段落，导致时间线面板渲染和滚动性能问题

**缓解措施：**
- 使用虚拟滚动（仅渲染可视区域节点）
- 实现节点懒加载（滚动时按需加载）
- 提供时间线密度控制选项（显示所有节点 / 仅显示有变化的节点）

### Risk 2: AI 工具调用导致状态不一致

**描述：** AI 修改角色状态可能与用户手动编辑冲突

**缓解措施：**
- 添加状态变更验证（检查冲突）
- 提供撤销/重做机制（复用现有 EventManager）
- 记录变更历史，支持回滚到任意时间点

### Risk 3: 数据模型兼容性

**描述：** 旧版故事文件可能缺少 `changes` 字段

**缓解措施：**
- `changes` 字段在添加段落时已初始化（见 state.js:137-140）
- 在渲染时添加容错处理，检查 changes 字段是否存在

### Risk 4: 时间线面板占用编辑空间

**描述：** 时间线面板可能在小屏幕上挤压段落编辑器

**缓解措施：**
- 默认折叠状态，用户主动展开
- 提供最小宽度限制（不低于 250px）
- 移动端支持全屏模式切换

### Trade-off: 功能丰富度 vs 实现复杂度

**描述：** 完整实现所有功能（状态回滚、冲突检测、高级筛选）将显著增加开发时间

**权衡：**
- 第一阶段实现核心功能（基础时间线、状态展示、AI 工具）
- 后续迭代增强功能（冲突检测、历史回滚、高级筛选）
- 保持接口扩展性，确保未来增强无需重构

## Migration Plan

### 部署步骤

1. **新增样式文件**
   - 创建 `css/timeline.css`

2. **修改现有模块**
   - 扩展 `js/managers/AIManager.js`，添加状态修改工具
   - 修改 `js/managers/UIRenderer.js`，添加时间线面板渲染方法
   - 扩展 `js/managers/EventManager.js`，添加时间线面板事件绑定

3. **更新 HTML**
   - 在段落编辑器容器中添加时间线面板 DOM 结构
   - 添加筛选按钮和折叠按钮

4. **测试验证**
   - 单元测试：AIManager 工具方法
   - 集成测试：时间线与段落同步、状态变更展示
   - UI 测试：展开/折叠、筛选、节点跳转

### 回滚策略

- 保留原有段落编辑器 DOM 结构，通过 CSS 类控制时间线面板显示/隐藏
- 数据使用现有的 `changes` 字段，回滚不影响数据完整性
- 修改仅限 UIRenderer 和 EventManager，回滚时移除相关代码即可

## Open Questions

1. **时间线节点粒度：** 是否支持显示段落内的多个状态变化点？（当前设计为段落级别）
2. **状态变化验证：** AI 修改角色状态时是否需要用户确认？（当前设计为自动修改，支持撤销）
3. **时间线导出：** 是否需要将时间线数据导出为独立格式？（当前设计为内嵌在段落数据中）
4. **多章节支持：** 时间线是否需要跨章节显示？（当前设计为单章节视图）
5. **角色情绪状态：** 情绪状态是否需要预定义枚举值？（当前设计为自由文本）
