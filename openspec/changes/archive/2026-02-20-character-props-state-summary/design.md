# Design: Character Props State Summary

## Context

当前 BailuStory 项目中，角色（Character）和道具（Item）的数据结构相对独立：
- 角色有基础属性、能力、情绪状态等字段
- 道具有属性、所有者（owner）字段指向角色 ID

系统支持段落级别的变化追踪（`changes.characters` 和 `changes.items`），在时间线上显示变化。但在段落状态摘要时，系统会显示所有角色和物品的状态，这导致信息过载。

约束条件：
1. 需要保持向后兼容，现有故事数据能正常加载
2. 状态摘要需要高效生成，不能引入显著性能问题
3. 道具和角色的关系需要保持一致性

## Goals / Non-Goals

**Goals:**
1. 扩展角色数据模型，支持 `heldItems` 字段，快速查询角色持有的道具
2. 优化段落状态摘要，只显示当前段落相关的角色和道具
3. 提供道具分配/转移的用户操作接口
4. 确保道具所有权和角色持有列表的一致性

**Non-Goals:**
1. 不实现复杂的道具管理系统（如道具合成、升级等）
2. 不改变现有的时间线变化追踪机制
3. 不实现道具的多人共享或借用功能
4. 不改变现有的段落编辑器 UI 结构

## Decisions

### Decision 1: 在 Character 对象中添加 heldItems 数组字段

**选择方案：**
在 `Character` 对象添加 `heldItems: string[]` 字段，存储道具 ID 列表

**替代方案：**
- **方案 A**：通过查询 Item 的 owner 字段反向查找角色持有的道具
  - 优点：无需修改角色数据结构，保持单一数据源
  - 缺点：每次查询都需要遍历所有道具，性能较差；无法快速获取角色持有的道具列表

- **方案 B**：使用独立的关系表（如 character_items）存储角色-道具关系
  - 优点：灵活支持复杂关系（借用、共享等）
  - 缺点：增加数据模型复杂度，当前场景无需如此复杂的关系

**决策理由：**
选择添加 `heldItems` 数组字段，因为：
1. 查询性能高，O(1) 时间复杂度获取角色持有的道具列表
2. 数据结构简单，与现有角色对象结构一致
3. 满足当前需求（一对一所有权关系）
4. 与 `owner` 字段互补，`heldItems` 作为缓存/索引

### Decision 2: 道具分配时同步更新 owner 和 heldItems

**选择方案：**
在 `PropsManager.setItemOwner(itemId, characterId)` 方法中，同时更新：
- Item 对象的 `owner` 字段
- 新角色对象的 `heldItems` 数组（添加 itemId）
- 旧角色对象的 `heldItems` 数组（移除 itemId）

**替代方案：**
- **方案 A**：只更新 owner 字段，heldItems 通过计算得出
  - 优点：单一数据源，避免同步问题
  - 缺点：每次查询都需要遍历道具列表，性能差

- **方案 B**：使用事件机制，触发 heldItems 自动更新
  - 优点：解耦，扩展性好
  - 缺点：增加复杂度，当前场景无需

**决策理由：**
选择同步更新方案，因为：
1. 保证数据一致性，避免 owner 和 heldItems 不一致
2. 实现简单直观，易于维护
3. 性能好，数据变更时一次性更新所有相关数据

### Decision 3: 段落状态摘要基于 changes.characters 筛选显示

**选择方案：**
段落状态摘要生成逻辑：
1. 查找当前段落的 `changes.characters`，获取出场的角色 ID 列表
2. 只显示这些角色的状态
3. 对于每个角色，只显示其 `heldItems` 中的道具状态
4. 忽略未在当前段落中出现的角色和道具

**替代方案：**
- **方案 A**：显示所有角色和道具的状态
  - 优点：完整信息
  - 缺点：信息过载，不相关内容干扰用户

- **方案 B**：基于用户关注度筛选（如最近编辑的角色）
  - 优点：个性化
  - 缺点：实现复杂，用户体验不一致

**决策理由：**
选择基于 `changes.characters` 筛选，因为：
1. 逻辑清晰，用户编辑哪个角色就显示哪个角色
2. 与段落变化追踪机制一致
3. 实现简单，无需额外状态管理
4. 符合用户预期（关注当前编辑的内容）

### Decision 4: 向后兼容性处理

**选择方案：**
1. 数据加载时，如果角色没有 `heldItems` 字段，默认初始化为空数组 `[]`
2. 数据修复脚本：根据 `items` 的 `owner` 字段重建 `heldItems` 数组
3. 不强制迁移，按需修复

**替代方案：**
- **方案 A**：强制迁移所有现有数据
  - 优点：数据一致性好
  - 缺点：迁移成本高，可能影响现有数据

- **方案 B**：不支持旧数据，要求用户手动修复
  - 优点：实现简单
  - 缺点：用户体验差

**决策理由：**
选择渐进式修复方案，因为：
1. 兼容现有数据，不影响现有用户
2. 按需修复，降低迁移风险
3. 修复脚本可以批量处理，效率高

## Risks / Trade-offs

### Risk 1: 数据不一致

**风险：** 道具的 `owner` 字段和角色的 `heldItems` 数组可能不同步，导致数据不一致。

**缓解措施：**
1. 封装道具分配逻辑，只通过 `PropsManager.setItemOwner()` 方法修改道具所有权
2. 在数据加载时校验数据一致性，不一致时以 `owner` 为准修复 `heldItems`
3. 添加数据验证逻辑，定期检查数据一致性

### Risk 2: 性能影响

**风险：** 段落状态摘要需要遍历多个数据结构，可能影响性能。

**缓解措施：**
1. 使用 Map 或 Set 优化数据查询性能
2. 缓存频繁查询的数据（如角色持有的道具列表）
3. 分页或懒加载状态摘要内容（如果数据量大）

### Trade-off 1: 数据冗余 vs 查询性能

**权衡：** `heldItems` 字段与 `owner` 字段存在数据冗余，但提高了查询性能。

**决策：** 选择数据冗余，因为：
1. 查询性能更重要（状态摘要频繁生成）
2. 数据量不大（单个角色通常持有 10 个以内的道具）
3. 冗余数据可以通过校验逻辑保证一致性

### Risk 3: 迁移复杂性

**风险：** 现有数据缺少 `heldItems` 字段，迁移逻辑可能复杂。

**缓解措施：**
1. 提供数据修复脚本，基于 `owner` 字段重建 `heldItems`
2. 在应用启动时检测数据，提示用户修复
3. 提供手动触发修复的入口（如设置菜单）

## Migration Plan

### 部署步骤

1. **代码部署**
   - 更新数据模型（Character 增加 `heldItems` 字段）
   - 更新 API（CharacterManager、PropsManager 新增/修改方法）
   - 更新 UI（角色编辑、道具分配、状态摘要）
   - 更新单元测试

2. **数据迁移**
   - 部署后，应用检测到数据缺少 `heldItems` 字段时，自动初始化为 `[]`
   - 提供数据修复脚本，根据 `items.owner` 重建 `heldItems`

3. **用户通知**
   - 在应用内显示提示："数据已升级，建议点击此处修复角色道具持有列表"
   - 用户点击后，执行数据修复脚本

4. **验证**
   - 测试现有数据加载是否正常
   - 测试道具分配/转移功能
   - 测试状态摘要显示逻辑

### 回滚策略

1. **代码回滚**
   - 恢复到旧版本代码
   - `heldItems` 字段会被忽略（旧代码不读取此字段）

2. **数据处理**
   - 旧版本不使用 `heldItems`，数据保持不变
   - 用户可能丢失部分修复数据（如 `heldItems` 数组），但不影响核心功能

## Open Questions

1. **道具转移历史是否需要记录？**
   - 当前需求未明确，可能需要扩展 `Item.changeHistory` 记录转移过程

2. **段落状态摘要的显示方式如何优化？**
   - 是否需要折叠/展开功能？
   - 是否需要高亮变化的内容？

3. **道具分配 UI 是否支持批量操作？**
   - 如一次性分配多个道具给一个角色
   - 如批量转移道具

4. **数据修复脚本是否需要自动执行？**
   - 自动修复可能影响大数据量的性能
   - 建议由用户手动触发，或提供自动/手动选项
